# 0005. Target C++20 with headers, not modules

Status: accepted
Date: 2026-08-09

## Context

Core, CoreTests and Graphite all set `cppdialect "C++20"` and `staticruntime
"on"`. Core and Graphite additionally set `warnings "High"` with
`fatalwarnings { "All" }`, so any warning fails the build; vendored projects do
not, and third-party headers come in through `externalincludedirs` with
`externalwarnings "Off"`. Sources are compiled `/utf-8`, both source and
execution charset, because the files are UTF-8 without a BOM and MSVC would
otherwise decode them through the machine's ANSI codepage.

Core carries a precompiled header, `corepch.h`. MSVC is the only compiler in
use; the build is generated by premake into a Visual Studio solution.

C++20 modules were considered at the outset and set aside. The build system,
not the compiler, is the binding constraint: premake's module support is not
something this project wants to depend on for the ability to build at all.

## Decision

The language is C++20. The mechanism for including code is `#include`. No
`import`, no module interface units, no header units.

C++20 language and library features are used freely where they earn their
place — concepts, `std::string_view`, designated initialisers, `<filesystem>`,
`<chrono>`. What is excluded is the modules build model, not the standard.

Raising the floor to C++23 is a separate decision and would need its own
record; `std::expected` is the feature most likely to prompt it, per
[0004](0004-return-result-t-instead-of-throwing-across-module-boundaries.md).

## Rationale

The build has to work every time, on one machine, with one toolchain, and be
regenerable from `GenerateProjects.bat`. Modules put that property at the mercy
of premake's generator and MSVC's module scanning, in exchange for compile times
that are not currently a problem. The exchange is bad at this size.

## Consequences

### Positive

- The build is boring, which is the property being bought.
- Every C++ tool, editor and static analyser understands the code, because it is
  ordinary translation units and headers.
- Dependencies are consumed the way they ship. Not one of the six vendored
  libraries offers a module interface.

### Negative

- Compile times stay header-bound and grow with the codebase, and `corepch.h`
  becomes load-bearing — adding to it speeds up a rebuild in the short term and
  couples everything to it in the long term.
- Include hygiene is permanent manual work: transitive includes, include-what-
  you-use discipline, and header ordering are all on the author, where modules
  would have made them structural.
- `warnings "High"` plus `fatalwarnings` means a warning in a header propagates
  the failure to every translation unit that includes it.

### Neutral

- MSVC-only. Nothing here forbids another compiler, but nothing has been built
  or tested against one, so the C++20 subset in use is really "what MSVC
  accepts". C++ Core Guidelines P.2 asks for ISO Standard C++; that is met by
  intent, not by a second compiler proving it.
- `staticruntime "on"` makes the executable self-contained. It is not a language
  decision and would not, on its own, need a record.

## Alternatives Considered

### C++20 with modules

The reason the standard has them: real build-time improvements and an end to
include-order fragility. Rejected on tooling, not on merit — premake would have
to generate a module-aware build reliably, and a failure there costs the ability
to build at all, which is a far worse outcome than a slow build. Reconsider when
premake's support is unremarkable.

### C++17

Broadest tool support and the safest possible floor. Rejected: it gives up
concepts, ranges, designated initialisers and `<format>`, and buys nothing this
project needs — the toolchain is a current MSVC either way.

### C++23

Would make `std::expected` available and let `Result<T>` become a thin alias
over it. Not chosen at the time: the project wanted a floor it was certain the
toolchain met without qualification. This is the alternative most likely to
return, and it would supersede this record rather than amend it.
